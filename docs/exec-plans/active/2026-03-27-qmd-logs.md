## Purpose / Big picture

After this work, Ariadne will expose a global QMD logs page at `/qmd/logs` that shows how agents used the QMD CLI across sessions, filtered by the existing global project scope selector. A user will be able to:

- open the main QMD page and see a scoped logs badge/button
- navigate to `/qmd/logs`
- browse detected QMD CLI calls in a table
- filter them by project scope, subcommand, search text, and error state
- open a modal to inspect the full command and the returned output

This must be implemented without increasing the data cost of Overview / Sessions / Usage initial loads. QMD log extraction should live in its own lazy cache and only run when a QMD logs endpoint is requested.

## Surprises & Discoveries

- Observation: The persisted session files already contain enough data to reconstruct QMD CLI usage without new instrumentation.
  Evidence: In pi session JSONL files, assistant `toolCall` blocks store the exact `bash` command and `toolCallId`, while matching `toolResult` messages store the output and `isError` under the same `toolCallId`.

- Observation: The original app shell hid project scope on QMD routes, but the shipped implementation now keeps project scope visible globally so `/qmd/logs` and the QMD logs badge can participate in the same scope model.
  Evidence: `src/app.tsx` now renders `ProjectScopeSelector` in the header without a QMD-route guard, while QMD pages keep their data loaders effectively unscoped.

- Observation: `/qmd/logs` needs explicit routing and breadcrumb handling so `logs` is not mistaken for a QMD index name.
  Evidence: `src/router.tsx` currently defines `/qmd/$index`, and `src/app.tsx` currently treats any `/qmd/:segment` path as an index breadcrumb.

- Observation: Reusing the existing QMD search UI directly would over-couple stateful code.
  Evidence: `src/components/qmd-search-modal.tsx` contains search behavior and rendering in one file. Reuse should happen by extracting read-only renderers, not by sharing modal state.

## Decision Log

- Decision: The logs route is global (`/qmd/logs`), not index-scoped.
  Rationale: The page observes how agents use the QMD CLI across sessions. Index metadata may still be parsed and displayed as a column/filter, but the route itself is not tied to a selected Ariadne QMD index.
  Date/Author: 2026-03-27 / user + agent

- Decision: The QMD badge counts all detected QMD calls, not only query-like commands.
  Rationale: The user explicitly wants visibility into overall QMD CLI usage. Subcommand-specific analysis can still happen inside the logs page.
  Date/Author: 2026-03-27 / user + agent

- Decision: Output must be shown in a modal/dialog.
  Rationale: Users need to inspect returned data to understand whether the agent got a useful answer. A modal keeps the table compact while preserving detail.
  Date/Author: 2026-03-27 / user + agent

- Decision: Use a dedicated lazy `QmdLogCache` instead of extending `SessionCache` initialization.
  Rationale: This keeps option B's caching benefits while avoiding additional cost on Overview / Sessions / Usage startup paths.
  Date/Author: 2026-03-27 / user + agent

- Decision: New QMD logs UI should be decomposed into pure display components under a focused folder.
  Rationale: The user explicitly wants isolated functional components with minimal side effects, aligned with React best practices.
  Date/Author: 2026-03-27 / user + agent

### Key patterns to preserve

- Route/page components own fetch effects and top-level state.
- Child components receive stable props and render only.
- Project scope remains globally stored in `ProjectScopeProvider`; QMD logs consume it, QMD index/collection pages remain effectively unscoped.
- Heavy session-derived parsing runs in dedicated backend code and is cached.

## Plan of work

### Milestone 1: Backend parser and models

Create backend types for a single QMD log entry and a small stats payload. Then add a focused parser module that reads one session JSONL file and returns zero or more QMD log entries.

The parser should:
- read the session header first for project/session identity
- track assistant `bash` tool calls by `toolCallId`
- detect QMD invocations by inspecting the bash command text
- correlate the matching `toolResult` by `toolCallId`
- attach output text and error status
- keep the raw command even when structured parsing fails

Keep command parsing best-effort. It is enough to reliably identify obvious subcommands (`query`, `search`, `get`, `multi-get`, `status`, `collection`, `context`, `embed`, `update`, `cleanup`, `ls`). Raw command text is the fallback truth.

### Milestone 2: Dedicated lazy cache

Add `QmdLogCache` as a separate managed state object in the Tauri app. It should mirror the overall shape of `SessionCache` but remain independent.

Expected behavior:
- lazy initialization on first QMD logs request
- build from discovered session files using the new parser module
- filter server-side by project path when returning results
- expose both `get_qmd_logs()` and `get_qmd_log_stats()` methods
- invalidate on `resync_sessions`

Run any full-cache build inside blocking work so it does not stall the async runtime.

### Milestone 3: Commands and app registration

Add a dedicated command module for QMD logs or extend an existing command module if the implementing agent has a strong reason. Register the new commands and new managed cache in `src-tauri/src/lib.rs`.

Update `resync_sessions` so it invalidates the QMD log cache after session resync finishes. The logs cache should rebuild lazily on the next logs request instead of eagerly during resync.

### Milestone 4: Frontend schemas, API, routing

Add Zod schemas and API wrappers for the two new endpoints:
- full log list
- small stats payload

Add a static `/qmd/logs` route in `src/router.tsx` and add a dedicated page component. Update `src/app.tsx` breadcrumb handling so `/qmd/logs` maps to `QMD / Logs` rather than `QMD / {index}`.

### Milestone 5: Project scope + logs badge integration

Change `src/app.tsx` so the project scope selector remains visible on QMD routes. Do not wire that scope into the existing QMD index/collection data loaders.

On `src/pages/qmd.tsx`, add a compact logs entry point with a badge. The badge must load independently of the page's main `fetch_data()` path. If log stats are still loading, show a lightweight loading placeholder and let the rest of the page render normally.

### Milestone 6: QMD logs page UI

Build `src/pages/qmd-logs.tsx` as a container component that:
- reads the active project scope
- fetches logs and stats in an effect
- owns search/filter state
- owns selected-row state for the output dialog
- passes already-shaped data into pure child components

Recommended child components:
- `QmdLogsStats`
- `QmdLogsToolbar`
- `QmdLogsTable`
- `QmdLogOutputDialog`

Derive filtered rows with `useMemo` instead of effect-driven state syncing. Hide the project column when a single project scope is active, following the Sessions page pattern.

### Milestone 7: Output dialog and viewer reuse

Implement the modal/dialog as a pure display component that receives the selected log entry and an `on_close` callback.

The dialog should render:
- timestamp/session/project metadata
- the full raw command
- status/error state
- full output text in a scrollable area

Optional structured rendering is encouraged when output is parseable as known QMD JSON. If reuse is desired from `qmd-search-modal.tsx`, extract read-only result renderers into focused components first. Do not reuse the search modal's fetch/progress state.

### Milestone 8: Docs and validation

Update `docs/information-architecture.md` to include the new QMD logs page and route semantics. If implementation adds notable backend architecture, update `docs/ARCHITECTURE.md` as well.

Then run build/type validation and complete manual app verification.

## Idempotence and recovery

- The new backend cache is read-only and session-derived. If parsing logic fails, it can be retried safely after fixes without changing persisted session data.
- If a cache invalidation bug appears, the safe fallback is to clear the in-memory QMD log cache and let it rebuild lazily.
- If structured output rendering proves unstable, keep the raw-output modal and defer structured rendering. The raw-output path is sufficient for a working first version.
- If route integration causes ambiguity with `/qmd/$index`, keep the static `/qmd/logs` route explicit and update breadcrumb special-casing before debugging any table issues.
