# QMD Logs — Global Agent Query Observability

Status: Draft
Date: 2026-03-27
Execution plan: `docs/exec-plans/active/2026-03-27-qmd-logs.md`

## 1. Problem statement

Ariadne currently lets users manage QMD indexes, collections, and search, but it does not expose how coding agents actually use QMD during sessions. The raw session data already contains enough information to reconstruct QMD CLI usage from `bash` tool calls, including the command string, the matched tool result, the project/session that issued it, and the resulting output.

This leaves two product gaps:

1. **No visibility into agent questions.** We cannot inspect what agents are asking QMD when repository docs or context are insufficient.
2. **No feedback loop for documentation quality.** We cannot use recurring QMD questions to identify missing docs, weak context setup, or opportunities to enrich QMD collections.

The goal of this feature is to add a global QMD logs page that turns those session artifacts into a browsable observability surface without coupling QMD log extraction to Ariadne's existing overview/session analytics load path.

## 2. Goals and non-goals

### 2.1 Goals
- Add a **global** QMD logs route at `/qmd/logs`.
- Show all detected QMD CLI calls made by agents through the `bash` tool.
- Filter logs by the existing global **project scope selector**.
- Re-enable the project scope selector on QMD routes so the logs page can participate in the same scope model as the rest of the app.
- Add a logs entry point on the main QMD page (`/qmd/:index`) with a badge showing the scoped count of QMD calls.
- Display the matched command output in a modal/dialog.
- Prefer a structured output viewer when the command output is parseable QMD JSON; otherwise fall back to a raw text view.
- Keep data loading **isolated** from Overview / Sessions / Usage so initial analytics loads do not pay for QMD log parsing.
- Follow React best practices: route-level data fetching, pure presentational child components, stable props, derived state instead of effect-driven UI state.

### 2.2 Non-goals
- Live tailing or streaming of QMD logs while a session is running.
- Automatic clustering, labeling, or summarization of documentation gaps.
- Mutating session data or retroactively rewriting session files.
- Perfect shell parsing for every possible `bash` command form; raw command text remains the source of truth.
- Index-scoped routing such as `/qmd/:index/logs`. Logs are global and may optionally expose parsed index metadata as a column/filter.
- Coupling QMD log extraction to `SessionCache` initialization for overview analytics.

## 3. System context

### 3.1 Existing backend behavior
- `src-tauri/src/cache.rs` provides `SessionCache`, which lazily parses all sessions and powers Overview, Sessions, Usage, and session detail.
- `src-tauri/src/parser/session.rs` already parses session JSONL files into `SessionSummary`, including aggregated tool usage and basic bash program counts.
- `src-tauri/src/commands/analytics.rs` exposes analytics/session commands backed by `SessionCache`.
- `src-tauri/src/lib.rs` currently manages `SessionCache` and `QmdSidecar` as separate application state.

### 3.2 Existing frontend behavior
- `src/app.tsx` hides the global project scope selector for all `/qmd` routes today.
- `src/router.tsx` currently has `/qmd`, `/qmd/:index`, and `/qmd/:index/:collection` routes only.
- `src/pages/qmd.tsx` is the QMD index overview page and is the correct place to add a logs entry point with a badge.
- `src/components/qmd-search-modal.tsx` already contains QMD result presentation patterns that can be reused if command output is parseable as structured QMD JSON.

### 3.3 Session-data facts that matter
The persisted pi session format stores enough information to reconstruct QMD CLI usage without new agent instrumentation:
- assistant `toolCall` content blocks contain the exact `bash` command string and `toolCallId`
- matching `toolResult` messages contain the output text and `isError`
- the session header contains project/session identity and timestamps

The reliable correlation key is `toolCallId`, not positional adjacency.

## 4. Conventions and style

- **Separate cache, separate lifecycle.** Implement QMD log extraction in a dedicated backend cache/module rather than extending `SessionCache`'s startup path.
- **Route container owns effects.** `src/pages/qmd-logs.tsx` should own fetching, scope-driven reloads, and modal state. Child components should be presentational.
- **Display components stay read-only.** Tables, filter bars, stat cards, and dialogs receive data and callbacks only. They should not fetch or mutate data themselves.
- **Prefer file-level decomposition.** New QMD logs UI should live under a focused folder such as `src/components/qmd-logs/` rather than growing `qmd.tsx` or `qmd-search-modal.tsx` into multi-purpose files.
- **Best-effort parsing with explicit fallback.** Store parsed metadata when available, but always keep `raw_command` and raw output as the canonical display fallback.
- **Asynchronous, non-blocking fetches.** Logs badge loading on `/qmd/:index` must not block index status/collection rendering.

## 5. Domain model

### 5.1 QMD log entry
A QMD log entry represents one detected QMD CLI invocation plus its matched tool result.

Suggested fields:
- `id` — stable unique ID such as `${session_id}:${tool_call_id}`
- `session_id`
- `project_path`
- `project_name`
- `timestamp` — when the command was issued
- `tool_call_id`
- `raw_command`
- `subcommand` — best-effort parsed value like `query`, `search`, `get`, `multi-get`, `status`, `collection`, `context`, `update`, `embed`, `cleanup`, `ls`, or `unknown`
- `index_name` — optional parsed index if detectable
- `collections` — parsed collection filters if detectable
- `primary_argument` — query text, document path, glob, or other main argument if detectable
- `is_error`
- `output_text` — full matched tool-result text from the session file
- `output_preview` — short preview for table display
- `output_kind` — `raw_text`, `search_json`, `files_json`, or other best-effort display hint

### 5.2 QMD log stats
A lightweight stats payload for badges and page summary cards.

Suggested fields:
- `total_calls`
- `error_calls`
- `unique_projects`
- `unique_sessions`
- `by_subcommand`

The main QMD page badge should use `total_calls`, scoped by the active project when present.

## 6. Detailed design

### 6.1 Backend cache architecture
Create a dedicated lazy cache for QMD logs, managed separately from `SessionCache`.

Recommended module split:
- `src-tauri/src/models/qmd_logs.rs`
- `src-tauri/src/parser/qmd_logs.rs`
- `src-tauri/src/qmd_log_cache.rs`
- `src-tauri/src/commands/qmd_logs.rs`

Recommended runtime behavior:
- `QmdLogCache::new()` is managed in `src-tauri/src/lib.rs` alongside `SessionCache`.
- The cache initializes only when `get_qmd_logs` or `get_qmd_log_stats` is invoked.
- Cache building should run in `spawn_blocking` or equivalent so UI-triggered commands do not block the async runtime.
- `resync_sessions` invalidates both `SessionCache` and `QmdLogCache` so future QMD log reads rebuild from fresh session files.

This preserves option B (cached extraction) while keeping the additional parsing off the Overview startup path.

### 6.2 Session parsing rules
Add a dedicated QMD log parser that reads session files directly instead of extending `SessionSummary`.

Parsing rules:
1. Read the session header first to capture `session_id`, `project_path`, and `project_name`.
2. Track assistant `toolCall` blocks where `name === "bash"` and the command contains a `qmd` invocation.
3. Key pending calls by `toolCallId`.
4. When a `toolResult` arrives with matching `toolCallId`, finalize the log entry with output text and `isError`.
5. If a pending QMD tool call never receives a tool result, keep it as an incomplete entry rather than dropping it silently.

Best-effort command parsing should detect:
- subcommand
- `-c` / `--collection` filters
- `--json`, `--files`, `--full`
- explicit index arguments if the command syntax exposes them
- primary query/path argument

The raw command string must still be stored and displayed even when parsing fails.

### 6.3 Tauri command surface
Add two dedicated commands instead of overloading analytics endpoints:
- `get_qmd_logs(project_path?: string)`
- `get_qmd_log_stats(project_path?: string)`

Design constraints:
- commands should apply the project filter server-side when provided
- command outputs should be typed and validated in frontend Zod schemas
- `get_qmd_log_stats` should be small enough to fetch independently for the `/qmd/:index` badge

### 6.4 Frontend route and scope behavior
Add a static route:
- `/qmd/logs` → global QMD logs page

Associated frontend updates:
- `src/router.tsx` must add a concrete `/qmd/logs` route
- `src/app.tsx` breadcrumbs must special-case `/qmd/logs` so `logs` is not mistaken for an index name
- `src/app.tsx` must stop hiding `ProjectScopeSelector` on QMD routes

Scope behavior:
- QMD index and collection pages keep their existing fetch behavior and remain effectively unscoped for QMD index data
- QMD logs page and QMD logs badge consume the active project scope
- changing project scope should not force index/collection pages to reload unrelated data

### 6.5 QMD page entry point
Add a lightweight QMD sub-navigation or action entry on `src/pages/qmd.tsx` that links to `/qmd/logs`.

Requirements:
- visually consistent with Ariadne's existing small tab/button groups
- includes a badge showing the scoped QMD call count
- badge data loads independently from the page's main QMD status/collection requests
- if stats are still loading, render a subtle placeholder rather than blocking the page

### 6.6 QMD logs page UI
Create a route container `src/pages/qmd-logs.tsx` that fetches logs and stats based on the active project scope.

Recommended composition:
- `QmdLogsHeader` or `QmdLogsNav` — global page title and any summary context
- `QmdLogsStats` — small stat cards using the stats payload
- `QmdLogsToolbar` — search input + subcommand filter + error-only toggle
- `QmdLogsTable` — DataTable-based list
- `QmdLogOutputDialog` — detail modal/dialog for the selected row

Suggested table columns:
- time
- project (hidden when scoped to a single project)
- session
- subcommand
- primary argument / query
- index (optional if detected)
- status
- output preview

The page component should own:
- fetched data
- search/filter state
- selected row for modal display

Child components should remain pure display components with memoizable props.

### 6.7 Output modal and viewer reuse
The output modal should prioritize usefulness over perfect normalization.

Behavior:
- always show command metadata and the full raw command
- show raw output in a readable scrollable area
- when output is parseable as known QMD JSON result formats, render a structured viewer above or beside the raw output

Reuse strategy:
- if the existing QMD search result cards are reused, extract the reusable presentation pieces from `src/components/qmd-search-modal.tsx` into focused presentational components rather than importing the entire modal
- keep search state and log-output state separate; only share read-only renderers

### 6.8 Performance and async loading
Performance constraints are part of the design, not an implementation afterthought.

Requirements:
- Overview, Sessions, and Usage must not trigger QMD log parsing.
- `/qmd/:index` must fetch log stats separately from index status/collections.
- QMD log cache build should happen on first logs/stats request and then be reused.
- server-side filtering by project should happen before sending payloads to the frontend.
- frontend filtering/search should operate on already-fetched scoped data, using derived state (`useMemo`) rather than effect-driven recalculation.

## 7. Error handling and failure modes

- **Malformed session lines**: skip individual lines and continue parsing the file.
- **Unparseable QMD commands**: still include the row with `subcommand: "unknown"` and the raw command.
- **Missing tool result**: mark the entry as incomplete and display a clear fallback message in the modal.
- **Large outputs**: preview fields should be truncated for table use, but the detail modal should preserve the full stored session output text.
- **Empty state**: if no QMD calls exist for the current scope, show an explicit empty state rather than an empty table.
- **Cache invalidation**: `resync_sessions` must invalidate stale QMD log cache data.

## 8. Security and safety considerations

- Treat all session-derived output as untrusted text. Do not inject it as HTML.
- Structured JSON rendering should only occur after explicit JSON parsing and schema validation.
- Display raw command text exactly; do not attempt to execute or re-run commands from the UI.

## 9. Testing strategy

### 9.1 Backend tests
- Unit-test QMD command detection and parsing with representative shell forms:
  - plain `qmd query "..."`
  - `cd repo && qmd query -c agents "..."`
  - `qmd search --json ... | jq ...`
  - non-QMD bash commands that must be ignored
- Unit-test assistant/tool-result correlation by `toolCallId`.
- Unit-test cache invalidation when `resync_sessions` runs.

### 9.2 Frontend/manual verification
- `bun run build`
- `cargo check --manifest-path src-tauri/Cargo.toml`
- manual app verification:
  - open `/qmd/:index` and confirm the logs badge loads without blocking index data
  - switch project scope and confirm the badge count changes
  - open `/qmd/logs` and confirm only scoped logs appear
  - open a row modal and confirm raw command + output render correctly
  - confirm project column hides when a specific project is scoped
