# Traces V2 — Jaeger-style Hierarchical Span Viewer

Status: Draft
Date: 2026-04-09
Execution plan: [[docs/exec-plans/active/2026-04-09-traces-v2.md]]

## 1. Problem statement

The current Traces view (`/sessions/:id/traces`) uses horizontal swim lanes grouped by role (user, assistant, tools, metadata). This works for a timeline overview but does not show the natural hierarchy of an agent session — a user prompt triggers an assistant response, which triggers tool calls, which produce results. Understanding the causal chain requires mentally reconstructing the nesting from flat lanes.

Traces V2 adds a Jaeger/Tempo-style hierarchical span viewer that renders the same session data as a collapsible tree with synchronized timeline bars, making the parent-child relationships between events explicit and navigable.

## 2. Goals and non-goals

### 2.1 Goals
- A new route `/sessions/:id/traces-v2` with its own tab in session detail nav
- Two-column layout: left = collapsible span tree, right = timeline bars
- Expand/collapse rows — collapsing a parent hides children and the parent bar covers the subtree duration
- Click a span row to show detail metadata in a sticky detail panel
- Reuse the existing `SessionDetailProvider` data (header + entries) — no new backend work
- Resizable divider between tree and timeline columns

### 2.2 Non-goals
- Replacing the existing traces view (v1 remains as-is)
- Modifying the JSONL format or backend replay-loader
- OpenTelemetry compatibility or external trace import
- Search/filter within the tree (can be added later)

### Key data constraint: parentId is a linear chain, not semantic nesting

The JSONL `parentId` field forms a singly-linked list: each entry points to the entry directly before it. It does **not** encode semantic parent-child relationships (e.g., tool calls are not children of the assistant message that issued them).

For the tree view to be useful, the transform must **synthesize a semantic hierarchy** from the linear chain:
- **Conversation turns** group entries into logical units: a user message, followed by an assistant response (with inline tool calls and results), forms one turn
- **Assistant content blocks** (text, thinking, tool calls) become children of the assistant span
- **Tool results** are paired with their tool calls via `toolCallId`
- **Metadata entries** (model_change, compaction, etc.) attach to the nearest preceding conversation turn or sit at root level

## 5. Domain model

### SpanNode — the tree element

Each node in the tree represents a logical unit of work in the session. A SpanNode has:
- An identity (derived from the underlying entry ID + optional content index)
- A label describing what it is ("User prompt", "tool: Read", "THINKING", etc.)
- Timing: start_ms and end_ms relative to session start
- Subtree timing: the earliest start and latest end across all descendants — used when the node is collapsed
- Children: ordered list of child SpanNodes
- Depth: nesting level for indentation
- Expandable: whether this node has children

### Hierarchy construction rules

The transform builds a semantic tree, not a parentId-chain tree:

1. **Root spans** are conversation turns — each begins with a user message (or session-start metadata)
2. **User message** → root-level span. Its children are the assistant responses that follow it (until the next user message)
3. **Assistant message** → child of the preceding user message. Its children are its content blocks:
   - Text blocks → leaf child
   - Thinking blocks → leaf child
   - Tool call blocks → child that may itself have a tool result child
4. **Tool result** → child of its matching tool call (matched by `toolCallId`)
5. **Metadata entries** (model_change, session_info, compaction, etc.) → root-level or attached to the nearest turn

### Collapse semantics

When collapsed:
- Children are hidden from the row list
- The parent's timeline bar extends to cover `subtree_start_ms` through `subtree_end_ms`
- The duration label updates to show the subtree duration

## 6. Detailed design

### Layout structure

The view has three main regions:
1. **Header bar** — span count, expand all / collapse all controls
2. **Main area** — split into left tree panel and right timeline panel with a resizable divider
3. **Detail panel** — appears below the main area when a span is selected (like Jaeger), showing entry metadata

The left tree and right timeline scroll together vertically — each row in the tree corresponds exactly to a row in the timeline. This is achieved by rendering both columns within the same scrollable container, with each row being a flex/grid row containing both the tree cell and the timeline cell.

### Timeline bar positioning

Bars are positioned using percentage-based left offset and width relative to the root span's total duration. Each bar shows:
- A colored bar (using existing chart color variables)
- Duration label to the left of the bar (e.g., "1.85ms", "24.93ms")

### Selection and detail

Clicking any row selects it (highlighted background). The detail panel shows:
- Span label, duration, start time offset
- Entry type, role
- Content preview (text content, tool arguments, tool results, thinking content)
- Token usage for assistant messages
- Raw JSON toggle

## 7. Error handling and failure modes

- Entries with unparseable timestamps: fall back to sequential ordering (index * 1000ms), same as v1
- Empty sessions: show an empty state message
- Entries that don't fit the hierarchy rules: attach at root level as standalone spans

## 8. Security and safety considerations

No new security surface — this is a read-only view of existing data with no new IPC or backend calls.

## 11. Open questions

1. **Gap compression** — should v2 reuse the same gap compression as v1, or show real (uncompressed) time? Real time makes the hierarchy clearer; compressed time makes long idle sessions more readable. **Recommendation**: start without compression, add it later if needed.
2. **Breadcrumb** — should `/sessions/:id/traces-v2` show as "Sessions / {id} / Traces V2" or something else? **Recommendation**: "Traces V2" for now, rename to "Traces" if v2 replaces v1 later.
